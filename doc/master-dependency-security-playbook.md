# Master Dependency Upgrade and Security Playbook

Universal playbook for Next.js, Tailwind CSS, frontend-only, and full stack JavaScript or TypeScript projects.

Last reviewed: 2026-05-31

## 1. Goal

Upgrade packages, migrate package management to pnpm where appropriate, remove known vulnerabilities, improve code security, improve code quality, and update runbooks without triggering remote deployments.

The desired end state is:

- One package manager per repo, preferably pnpm
- One committed lockfile, preferably `pnpm-lock.yaml`
- Exact dependency versions in `package.json` after clean candidates are selected
- No known high or critical package vulnerabilities unless explicitly documented as accepted risk
- Build, lint, type check, unit tests, integration tests, and E2E tests pass locally
- Security-sensitive code paths reviewed and hardened
- Runbooks and manual deployment notes updated
- No push, no merge, no deploy, no remote branch creation

## 2. Non-negotiable constraints

1. Do not push to any remote.
2. Do not create remote branches.
3. Do not deploy to Vercel or any other host.
4. Do not run tests against production URLs, production databases, or production credentials.
5. Run all app tests against `localhost` or `127.0.0.1` only.
6. Do not delete user work. Preserve uncommitted changes unless they are generated by this task.
7. Do not hide failing tests. Fix them or document the exact reason they could not be fixed.
8. Do not use prerelease, beta, canary, alpha, or release candidate packages unless an official migration tool requires it or a security advisory makes it mandatory.
9. Do not accept a package candidate that is less than 7 days old unless it fixes a known vulnerability and no safe older patched version exists.
10. At the end, produce a manual actions section even when no manual actions are needed.

## 3. Source of truth order

Use this order when researching upgrades:

1. Official package docs, official changelogs, official upgrade guides, and official security advisories
2. npm registry metadata, including publish times and dist tags
3. GitHub Security Advisories, OSV, npm audit, NVD, and vendor advisories
4. Vercel docs for deployment-specific behavior
5. Community notes only when official docs are silent, and clearly label them as lower confidence

Use web search and Context7 for current package docs. Context7 should be used for library usage details when available. Web search should be used for latest releases, advisories, Vercel behavior, and breaking changes.

## 4. Version candidate policy

For every package candidate:

1. Verify the package name is the intended package and not a typo-squatting or package confusion risk.
2. Reject prereleases by default. Reject versions containing `alpha`, `beta`, `canary`, `next`, `rc`, or similar prerelease markers unless there is a documented exception.
3. Check the npm publish time.
4. Prefer the newest stable version that is at least 7 days old.
5. If the latest stable version is younger than 7 days, choose the newest stable version that is at least 7 days old.
6. If a CVE, GHSA, OSV, or npm advisory requires a patched version that is younger than 7 days, use the patched version and document the exception.
7. For major upgrades, read the official migration guide before changing versions.
8. For ecosystem packages, upgrade compatible sets together. Examples include `next`, `react`, `react-dom`, `eslint-config-next`, Tailwind packages, TypeScript, ESLint, Playwright, Vitest, Jest, and Testing Library.
9. After selecting a clean candidate, save it as an exact version.

Useful checks:

```bash
pnpm view <package> dist-tags --json
pnpm view <package> versions --json
pnpm view <package> time --json
pnpm view <package>@<version> peerDependencies --json
pnpm view <package>@<version> engines --json
```

Use exact additions:

```bash
pnpm add <package>@<version> --save-exact
pnpm add -D <package>@<version> --save-exact
```

## 5. pnpm policy

### 5.1 Package manager selection

Default to pnpm unless the repository has a hard blocker. If the project is hosted on Vercel, verify the pnpm major version supported by Vercel at the time of work before pinning `packageManager`.

For Vercel projects, prefer this order:

1. Let Vercel detect pnpm from `pnpm-lock.yaml` when no custom install command is required.
2. If a Vercel install command override is required, set it explicitly and document it.
3. If using Corepack through Vercel, verify Vercel support first and document any required environment variables.
4. Do not pin a pnpm major that Vercel does not support unless the owner accepts the deployment risk.

### 5.2 Migration from npm to pnpm

When the repo currently uses npm:

1. Record baseline state.
2. Confirm `package-lock.json` exists and `pnpm-lock.yaml` does not already exist.
3. Create or update `pnpm-workspace.yaml` first if this is a workspace.
4. Run `pnpm import` to generate `pnpm-lock.yaml` from the existing lockfile.
5. Run `pnpm install` and resolve peer dependency issues.
6. Remove `package-lock.json` only after `pnpm-lock.yaml` is valid and tests pass.
7. Update local scripts, docs, GitHub Actions, and Vercel instructions from npm to pnpm.
8. Keep one lockfile.

Recommended config in `pnpm-workspace.yaml` for a root project:

```yaml
packages:
  - .

minimumReleaseAge: 10080
minimumReleaseAgeStrict: true
```

For monorepos, replace the package list with the actual workspace layout:

```yaml
packages:
  - apps/*
  - packages/*

minimumReleaseAge: 10080
minimumReleaseAgeStrict: true
```

Use `minimumReleaseAgeExclude` only for documented security exceptions:

```yaml
minimumReleaseAgeExclude:
  - package-name
```

### 5.3 Install and lockfile discipline

Use local install commands during remediation:

```bash
pnpm install
pnpm install --frozen-lockfile
```

Use `pnpm install --frozen-lockfile` in CI-style validation because it fails when the lockfile and manifests are out of sync.

Do not use `--force`, broad overrides, or ignored peer dependency errors as a permanent fix. Use them only to diagnose, then remove them.

## 6. Preflight checklist

Run these checks before modifying dependencies:

```bash
git status --short
git branch --show-current
git remote -v
node --version
corepack --version || true
pnpm --version || true
npm --version || true
find . -maxdepth 3 -name package.json -not -path '*/node_modules/*'
find . -maxdepth 3 \( -name package-lock.json -o -name pnpm-lock.yaml -o -name yarn.lock -o -name bun.lock -o -name bun.lockb \)
```

Inspect:

- `package.json`
- Existing lockfiles
- `next.config.*`
- `tailwind.config.*`
- `postcss.config.*`
- `tsconfig.json`
- `eslint.config.*` or `.eslintrc.*`
- `playwright.config.*`, `vitest.config.*`, `jest.config.*`, and Cypress config files
- `.github/workflows/*`
- `vercel.json`
- `README*`, `RUNBOOK*`, `CONTRIBUTING*`, and deployment docs
- `.env.example` and local environment docs

Create a baseline report in `doc/maintenance/dependency-upgrade-report.md` or an equivalent existing runbook path.

## 7. Inventory and risk map

Classify the project:

- Frontend-only Next.js app
- Full stack Next.js app with route handlers, API routes, server actions, middleware, database, auth, or background jobs
- Static site with build-time data fetching
- Monorepo or single package repo

Inventory sensitive areas:

- Authentication and session handling
- Authorization checks
- User input validation
- API routes and route handlers
- Server actions
- Middleware
- Database queries and ORM usage
- File uploads and image processing
- Webhooks
- Payment or billing code
- Email sending
- Third-party scripts
- Analytics and tag managers
- CSP and security headers
- Environment variable use
- Logging and error reporting
- Dependency postinstall scripts

## 8. Package upgrade workflow

### 8.1 Baseline dependency scan

Run available commands. Use what exists in the repo and add missing scripts only when useful.

```bash
pnpm outdated --format json || pnpm outdated || true
pnpm audit --audit-level=moderate || true
pnpm audit --prod || true
```

If OSV-Scanner is available:

```bash
osv-scanner scan .
```

If GitHub CLI is available and authenticated:

```bash
gh api repos/:owner/:repo/dependabot/alerts --paginate || true
```

### 8.2 Upgrade planning

Build an upgrade table:

| Package | Current | Candidate | Candidate age | Reason | Advisory | Breaking changes | Action |
|---|---:|---:|---:|---|---|---|---|
| next | current | candidate | days | framework upgrade | CVE or none | link or note | exact update |

Group updates:

1. Package manager and lockfile migration
2. Framework core, for example Next.js, React, React DOM
3. Styling stack, for example Tailwind, PostCSS, Autoprefixer
4. TypeScript and type packages
5. Linting and formatting
6. Testing tools
7. Runtime server libraries
8. Security-sensitive libraries, for example auth, validation, database, crypto, upload, image, markdown, sanitize, JWT, cookies
9. Minor utility packages

### 8.3 Apply updates in small batches

Recommended batch order:

1. Package manager migration
2. Security patch updates with no breaking changes
3. Framework minor or patch updates
4. Framework major updates with official codemods
5. Tailwind major update with official upgrade tool only if browser support allows it
6. Testing and linting tools
7. Remaining packages

After each batch:

```bash
pnpm install
pnpm install --frozen-lockfile
pnpm run lint || true
pnpm run typecheck || true
pnpm test || true
pnpm run build || true
```

Replace commands with actual repo scripts when names differ.

### 8.4 CVE remediation rules

For each advisory, record:

- Advisory ID
- Package
- Direct or transitive dependency
- Affected range
- Installed version
- Minimum patched version
- Selected version
- Whether the 7-day maturity rule was bypassed
- Why the selected version is safe
- Test evidence

Resolution order:

1. Upgrade the direct dependency to a patched version.
2. If vulnerability is transitive, upgrade the parent package that pulls it in.
3. If no parent update exists, use `pnpm.overrides` or root `pnpm-workspace.yaml` overrides as a temporary documented mitigation.
4. If no patched path exists, replace the package or document accepted residual risk.
5. Remove temporary overrides once upstream packages catch up.

When pnpm 11 or newer is allowed in the project and supported by the deployment target, `pnpm audit --fix=update --interactive` can be used for guided vulnerability fixes. Otherwise perform explicit version updates and document the reason.

## 9. Next.js upgrade workflow

1. Identify current Next.js major and target major.
2. Read the official upgrade guide for every crossed major version.
3. Use official codemods when recommended.
4. Upgrade compatible framework packages together:

```bash
pnpm add next@<version> react@<version> react-dom@<version> eslint-config-next@<version> --save-exact
```

5. Check changes in:

- App Router and Pages Router behavior
- Server components
- Server actions
- Route handlers
- Middleware
- Image config
- Headers and redirects
- Environment variable behavior
- Caching and revalidation
- Fetch behavior
- ESLint config
- TypeScript config

6. Run:

```bash
pnpm run build
pnpm run dev
```

Open the app only on `http://localhost:<port>` or `http://127.0.0.1:<port>`.

## 10. Tailwind CSS upgrade workflow

1. Identify current Tailwind major.
2. Read the official Tailwind upgrade guide for the target major.
3. Check browser support requirements before moving to a new major.
4. If moving from Tailwind 3 to 4, use the official upgrade tool only after making a clean local working state.
5. Validate changes in:

- Global CSS imports
- PostCSS config
- Tailwind config migration
- Custom theme tokens
- Plugins
- Content paths
- Class name changes
- Dark mode behavior
- Animations
- Forms and typography plugins

6. Run visual checks locally with the development server.
7. Run E2E tests for core screens.

## 11. Code security review checklist

### 11.1 Universal checks

Search for:

```bash
rg "dangerouslySetInnerHTML|eval\(|new Function|innerHTML|document.write|localStorage|sessionStorage|process.env|NEXT_PUBLIC_|TODO|FIXME|password|secret|token|api[_-]?key" .
```

Review and fix:

- XSS sinks
- Unsafe HTML rendering
- Unsanitized markdown or rich text
- Unsafe redirects
- Open redirects
- Insecure use of `target="_blank"`
- Secrets committed in files
- Secrets exposed through `NEXT_PUBLIC_`
- Excessive client-side token storage
- Missing input validation
- Missing error boundaries for risky surfaces
- Sensitive data in logs
- Weak crypto usage
- Outdated auth libraries
- Overly permissive CORS
- Missing CSRF protection for cookie-based mutation flows
- Missing authorization checks on server routes
- SSRF-prone URL fetches
- SQL or NoSQL injection risks
- Insecure file upload validation
- Unbounded request body sizes
- Missing rate limits on sensitive endpoints

### 11.2 Next.js frontend-only checks

Review:

- Client components that render external content
- Third-party scripts and analytics tags
- Image domains and remote patterns
- Environment variables exposed to the browser
- Redirect and rewrite rules
- CSP and other security headers
- Forms that send data to third parties
- Dependency use in browser bundles

### 11.3 Full stack checks

Review:

- API routes
- Route handlers
- Server actions
- Middleware
- Auth callbacks
- Cookie settings
- Session expiration and rotation
- Authorization boundaries
- Database access patterns
- Webhook signature verification
- File upload type, size, and storage rules
- Rate limiting
- Error responses that leak internals
- Local-only test data and seed scripts

Cookie targets:

- `HttpOnly` for session cookies
- `Secure` in production
- `SameSite=Lax` or stricter where compatible
- Narrow path and domain
- Explicit expiration

## 12. Code quality review checklist

Run the project scripts or add them if absent and appropriate:

```bash
pnpm run lint
pnpm run typecheck
pnpm run format:check
pnpm test
pnpm run test:unit
pnpm run test:integration
pnpm run test:e2e
pnpm run build
```

Review:

- TypeScript strictness
- Dead code
- Unused dependencies
- Duplicate dependencies
- Deprecated APIs
- Excessive `any`
- Unhandled promises
- Inconsistent error handling
- Flaky tests
- Missing tests around security-sensitive paths
- Large client bundles caused by server-only packages imported into client components
- Accessibility regressions on key pages

Optional tools when already present or easy to add safely:

```bash
pnpm dlx knip
pnpm dlx depcheck
pnpm dlx ts-prune
pnpm dlx eslint .
pnpm dlx prettier . --check
```

Do not add tools permanently unless they provide clear value and pass the 7-day package rule.

## 13. Local test protocol

1. Create or update `.env.example` without secrets.
2. Use `.env.local` only for local development.
3. Replace production URLs with localhost or mocks.
4. For full stack apps, use a local database, local test container, local emulator, or mocked service.
5. Never run destructive migrations on production.
6. Seed only local test data.
7. Start the local app:

```bash
pnpm run dev
```

8. Run E2E tests only against local URL:

```bash
BASE_URL=http://127.0.0.1:3000 pnpm run test:e2e
```

9. Capture command output and failures in the upgrade report.

## 14. Vercel-specific manual action checklist

The agent must not change Vercel dashboard settings. It must report needed manual changes.

At the end, check and report:

- Whether `pnpm-lock.yaml` exists and old npm or Yarn lockfiles were removed
- Whether `package.json` has a compatible `packageManager` field
- Whether Vercel install command should be removed to allow auto-detection
- Whether Vercel install command should be changed from `npm install` to `pnpm install --frozen-lockfile`
- Whether Vercel build command should be changed from `npm run build` to `pnpm run build`
- Whether Vercel development command should be changed from `npm run dev` to `pnpm run dev`
- Whether Vercel Node.js version must be updated
- Whether Corepack must be enabled, only when the selected Vercel setup requires it
- Whether environment variables need to be updated
- Whether GitHub Actions or other CI workflows need npm commands replaced
- Whether Dependabot or another dependency update tool should be enabled or updated for pnpm

## 16. Acceptance gates

The work is not complete until:

1. `pnpm install --frozen-lockfile` passes locally.
2. `pnpm audit --audit-level=moderate` has no unresolved high or critical findings, unless documented as accepted risk.
3. OSV scan is clean or documented.
4. Lint passes or every remaining lint failure is documented with file paths and reason.
5. Type check passes or every remaining type error is documented with file paths and reason.
6. Unit tests pass or failures are documented with root cause.
7. E2E tests pass locally or blockers are documented with exact local setup gaps.
8. `pnpm run build` passes locally.
9. Security-sensitive code review is complete.
10. Runbooks are updated.
11. Manual Vercel and CI actions are listed.
12. No remote push, merge, deployment, or production test occurred.

## 17. Rollback plan

Before finishing, document:

- Files changed
- Lockfile migration details
- Commands needed to reinstall dependencies
- How to return to the previous package manager if required
- How to revert package updates with git
- Any database or local migration changes
- Any manual Vercel settings that should not be changed until review
